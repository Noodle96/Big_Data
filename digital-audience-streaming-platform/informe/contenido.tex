\section{Infraestructura (Pulumi / AWS Academy)}

Toda la infraestructura del proyecto (Kafka, Flink, PostgreSQL/TimescaleDB y Grafana) se define como código con Pulumi (Python) y se despliega sobre AWS Academy. El script completo vive en \texttt{infra/\_\_main\_\_.py}; esta sección documenta el despliegue paso a paso, con la evidencia real de cada comando ejecutado y su verificación.

\subsection{Despliegue con Pulumi}

Con el stack ya configurado, el despliegue completo de las 8 instancias y su red se ejecuta con un solo comando:

\inlinesourcecodeboxed[cmdbg]{bash}{pulumi up --yes}

La Figura \ref{img:pulumi-up-1} muestra el resultado de ese comando: Pulumi identifica y crea los 8 recursos \texttt{aws:ec2:Instance} correspondientes a las filas de la Tabla \ref{tab:instancias-ec2}.

\insertimage[\label{img:pulumi-up-1}]{evidencia/pulumi-up-1.png}{width=14cm}{Resultado de \texttt{pulumi up --yes}: 8 recursos \texttt{aws:ec2:Instance} creados.}

Al terminar, Pulumi imprime los outputs exportados por el stack (Figura \ref{img:pulumi-up-2}): el string de \texttt{bootstrapServers} para Kafka, las URLs de Flink y Grafana, y las IPs privadas/públicas de cada instancia -- estos son los valores que se usan en el resto de esta sección para armar los comandos \texttt{ssh}.

\insertimage[\label{img:pulumi-up-2}]{evidencia/pulumi-up-2.png}{width=14cm}{Outputs de \texttt{pulumi up --yes}: endpoints y comandos SSH de cada instancia.}

Un detalle importante que se comprobó en esta corrida: que \texttt{pulumi up} termine no significa que Kafka/Flink/Postgres/Grafana ya estén instalados y corriendo -- eso lo hace el script de \texttt{user\_data} (cloud-init) en segundo plano dentro de cada instancia, y toma varios minutos adicionales. Las siguientes subsecciones verifican, servicio por servicio, que ese proceso terminó correctamente.

\subsection{Verificación: Apache Kafka (KRaft)}

Los 3 brokers corren Kafka 3.9.0 en modo KRaft (sin Zookeeper), reutilizando el patrón validado en el laboratorio anterior del curso (incluyendo el fix del bug KAFKA-18281). En cada broker se verifica que el servicio systemd \texttt{kafka} esté activo con \texttt{systemctl status}, forzando un pseudo-terminal (\texttt{-t}) para que la salida se trunque al ancho de la consola en vez de imprimir la línea completa del proceso Java.

En kafka-broker-1 (10.30.1.11, IP pública 54.234.134.254):

\begin{lstlisting}[style=cmdbox]
ssh -t -i ../keys/audiencias-lab-key.pem \
  ubuntu@54.234.134.254 \
  "sudo systemctl status kafka --no-pager"
\end{lstlisting}

La Figura \ref{img:status-kafka-1} confirma que el servicio quedó \texttt{active (running)} en kafka-broker-1, arrancado como \texttt{nodeId=1} del quorum KRaft.

\insertimage[\label{img:status-kafka-1}]{evidencia/status-kafka-broker-1.png}{width=14cm}{Servicio \texttt{kafka} activo en kafka-broker-1 (nodeId=1).}

Se repite el mismo comando, cambiando solo la IP, en kafka-broker-2 (10.30.1.12, IP pública 54.87.246.253):

\begin{lstlisting}[style=cmdbox]

  ubuntu@54.87.246.253 \
  "sudo systemctl status kafka --no-pager"

La Figura \ref{img:status-kafka-2} confirma el mismo resultado en kafka-broker-2 (\texttt{nodeId=2}).

\insertimage[\label{img:status-kafka-2}]{evidencia/status-kafka-broker-2.png}{width=14cm}{Servicio \texttt{kafka} activo en kafka-broker-2 (nodeId=2).}

\subsection{Verificación: PostgreSQL + TimescaleDB}

La instancia dashboard (10.30.1.30, IP pública 98.81.129.129) corre PostgreSQL 16 con la extensión TimescaleDB, que será el destino de los datos agregados que escriba Flink (Fase 4 del plan de trabajo). Se verifica en tres pasos: el servicio, el cluster de Postgres, y la extensión.

\begin{lstlisting}[style=cmdbox]
ssh -t -i ../keys/audiencias-lab-key.pem \
  ubuntu@98.81.129.129 \
  "sudo systemctl status postgresql --no-pager"
\end{lstlisting}

La Figura \ref{img:status-pg} muestra el servicio \texttt{postgresql} activo -- aunque en estado \texttt{active (exited)} en vez de \texttt{running}, que es el comportamiento esperado: ese servicio es solo un orquestador, por diseño de los paquetes de Debian/Ubuntu.

\insertimage[\label{img:status-pg}]{evidencia/status-postgresql.png}{width=14cm}{Servicio \texttt{postgresql} (envoltorio de Debian/Ubuntu) activo.}

Para confirmar que la instancia real de Postgres (\texttt{16/main}) está en línea de verdad:

\begin{lstlisting}[style=cmdbox]
ssh -i ../keys/audiencias-lab-key.pem \
  ubuntu@98.81.129.129 \
  "sudo pg_lsclusters"
\end{lstlisting}

La Figura \ref{img:pg-lsclusters} confirma el cluster \texttt{16/main} en estado \texttt{online}, escuchando en el puerto 5432.

\insertimage[\label{img:pg-lsclusters}]{evidencia/postgres-lsclusters.png}{width=14cm}{Cluster \texttt{16/main} en estado \texttt{online}, puerto 5432.}

Y por último, que la extensión TimescaleDB quedó correctamente instalada en la base \texttt{audiencias}:

\begin{lstlisting}[style=cmdbox]
ssh -i ../keys/audiencias-lab-key.pem \
  ubuntu@98.81.129.129 \
  "PGPASSWORD='AudienciasLab2026!' psql -h localhost \
   -U flink -d audiencias -c '\dx'"
\end{lstlisting}

La Figura \ref{img:pg-timescale} confirma la extensión \texttt{timescaledb} (versión 2.29.0) instalada en la base \texttt{audiencias}, cerrando la verificación de esta instancia.

\insertimage[\label{img:pg-timescale}]{evidencia/postgres-timescaledb-extension.png}{width=14cm}{Extensión \texttt{timescaledb} (v2.29.0) instalada en la base \texttt{audiencias}.}
