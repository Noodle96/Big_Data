\section{Arquitectura de la solución}
\label{sec:arquitectura}

La plataforma sigue una Arquitectura Orientada a Eventos de punta a punta: cada acción de un usuario simulado se convierte en un evento que viaja por el sistema sin que ningún componente conozca directamente a los demás -- solo se comunican a través de Kafka. La Figura \ref{img:pipeline-general} resume el flujo completo.

\insertimage[\label{img:pipeline-general}]{diagramas/pipeline-general.png}{width=15cm}{Pipeline general: Agentes → Productores Kafka → Apache Kafka → Apache Flink → PostgreSQL/TimescaleDB → Grafana.}

Los agentes autónomos (Sección \ref{sec:fase2}) simulan usuarios reales con 8 perfiles de comportamiento distintos. Cada acción que decide tomar un agente se serializa como un evento JSON y se publica a Kafka a través de uno de 5 canales (web, mobile, IoT, vehicle, POS). Kafka (Sección \ref{sec:infraestructura}) recibe, replica y almacena esos eventos en los 2 topics diseñados por semántica de negocio (Sección \ref{sec:kafka-topics}), sin procesarlos -- solo los deja disponibles para quien los consuma. Apache Flink, corriendo como cluster real (JobManager + 3 TaskManagers), consume esos eventos de forma continua y aplicará sobre ellos el filtrado, enriquecimiento y las reglas de negocio que construyen las audiencias digitales (Fase 4/5, pendientes). Los resultados agregados se escriben a PostgreSQL/TimescaleDB, que Grafana consulta periódicamente para redibujar el dashboard en tiempo real (Fase 6, pendiente).

Tres decisiones de arquitectura se tomaron explícitamente antes de empezar a construir, y se mantienen a lo largo de todo el proyecto:

\textbf{Flink como cluster real, no embebido.} A diferencia del laboratorio anterior del curso (un solo proceso Java consumiendo Kafka), acá se optó por un cluster real con JobManager y TaskManagers separados, más fiel a un entorno productivo y que permite observar paralelismo, checkpoints y una Web UI real.

\textbf{Grafana + PostgreSQL/TimescaleDB para el dashboard}, en vez de un dashboard propio (Streamlit) o una arquitectura 100\% push vía WebSockets. Se evaluaron las tres opciones: WebSockets es la más fiel al espíritu de "arquitectura orientada a eventos de punta a punta" (el propio dashboard sería un consumidor más), pero implica mucho más código propio; Grafana ofrece paneles y alertas por umbral ya integrados, a costa de una actualización por consulta periódica en vez de empuje instantáneo -- una diferencia aceptable para los fines de este proyecto.

\textbf{Infraestructura como código con Pulumi sobre AWS Academy}, reutilizando el patrón ya validado en el laboratorio de Kafka del curso (VPC, IPs privadas estáticas, todo el bootstrap dentro de \texttt{user\_data}, cero configuración manual por SSH), extendido con los componentes nuevos de este proyecto.

\section{Infraestructura (Pulumi / AWS Academy)}
\label{sec:infraestructura}

Toda la infraestructura del proyecto (Kafka, Flink, PostgreSQL/TimescaleDB y Grafana) se define como código con Pulumi (Python) y se despliega sobre AWS Academy. El script completo vive en \texttt{infra/\_\_main\_\_.py} del \href{https://github.com/Noodle96/Big_Data/tree/main/digital-audience-streaming-platform}{repositorio del proyecto en GitHub}; esta sección documenta el despliegue paso a paso, con la evidencia real de cada comando ejecutado y su verificación.

\subsection{Componentes utilizados y su propósito}

Antes de entrar en el despliegue concreto, esta subsección describe qué es cada pieza de la infraestructura y qué rol cumple dentro del pipeline completo (Agentes → Kafka → Flink → PostgreSQL/TimescaleDB → Grafana).

\textbf{Pulumi.} Herramienta de infraestructura como código (IaC): define y despliega todos los recursos de AWS mediante un programa Python, en vez de crearlos manualmente desde la consola. Permite reproducir el cluster completo con un solo comando (\texttt{pulumi up}) y destruirlo igual de fácil (\texttt{pulumi destroy}), algo clave para no consumir horas del Learner Lab de AWS Academy sin necesidad.

\textbf{Apache Kafka (modo KRaft).} La capa de mensajería del proyecto: recibe los eventos publicados por el simulador de agentes y los distribuye a quien los necesite consumir (en este caso, Flink). Corre en modo KRaft (sin Zookeeper), con 3 brokers que además actúan como controllers del quorum, replicando los datos entre sí para tolerar la caída de uno.

\textbf{Apache Flink (cluster real: JobManager + TaskManagers).} El motor de procesamiento de streaming: consume continuamente los eventos desde Kafka, aplica las reglas de negocio (filtrado, enriquecimiento, ventanas de tiempo, clasificación de audiencias) y escribe los resultados agregados a la base de datos. El JobManager coordina la ejecución y el estado del cluster; los TaskManagers son los que realmente ejecutan las tareas en paralelo.

\textbf{PostgreSQL + TimescaleDB.} La base de datos donde Flink escribe sus resultados. PostgreSQL es la base relacional; TimescaleDB es una extensión sobre PostgreSQL (no una base aparte) que agrega manejo eficiente de series de tiempo, útil porque casi todas las métricas del proyecto (usuarios activos, eventos por segundo, tendencias, etc.) son datos que cambian en el tiempo.

\textbf{Grafana.} El motor de visualización del dashboard. No almacena nada: se conecta a PostgreSQL/TimescaleDB como cliente de solo lectura y consulta cada pocos segundos para redibujar los paneles en tiempo real.

\textbf{VPC y Security Group compartido.} Todas las instancias viven en la misma red privada (\texttt{10.30.0.0/16}) y comparten un único Security Group, que permite todo el tráfico interno entre ellas (necesario para que Kafka, Flink y Postgres se comuniquen) pero solo expone a Internet los puertos estrictamente necesarios para operar desde afuera: SSH (22), la Web UI de Flink (8081) y Grafana (3000).

\textbf{Cliente (kafka-client).} La instancia desde donde se corre el simulador de agentes (Fase 2) y el script de creación de topics (\texttt{scripts/kafka/create\_topics.py}). No corre ningún servicio permanente -- durante el arranque solo deja Python y un entorno virtual (venv) listos; el código del proyecto se sube por separado con \texttt{rsync} (Sección \ref{subsec:ampliacion-cliente}), no se clona por git. Es una sola instancia para productor y verificación de consumo (no dos separadas, como en el laboratorio anterior), para no sumar más EC2 al Learner Lab.

\textbf{\texttt{escenarios/seasons.py}: temporada comercial activa.} Detecta en qué temporada está la simulación (por fecha real, o forzada explícitamente) y devuelve un \texttt{purchase\_boost} e \texttt{intensity} que modifican el comportamiento de todos los agentes -- así, en Navidad o Cyber Monday, la probabilidad de compra sube sin tener que tocar los perfiles de agente.

\begin{sourcecode}[\label{code:seasons}]{python}{Detección de temporada por fecha real (\texttt{escenarios/seasons.py}).}
def _season_by_calendar_date(d: date) -> Season:
    if d.month == 11 and 28 <= d.day <= 30:
        return SEASONS["cyber_monday"]
    if d.month == 12 and 1 <= d.day <= 25:
        return SEASONS["navidad"]
    if d.month == 7 and 25 <= d.day <= 29:
        return SEASONS["fiestas_patrias"]
    # ... dia_del_padre, campaña_escolar, black_friday
    return SEASONS["normal"]
\end{sourcecode}

\textbf{\texttt{productores/producers.py}: publicación en Kafka.} Una clase base (\texttt{BaseProducer}) concentra la conexión al cluster y el envío; 5 clases heredan de ella para modelar los 5 canales del enunciado (\texttt{WebProducer}, \texttt{MobileProducer}, \texttt{IoTProducer}, \texttt{VehicleProducer}, \texttt{POSProducer}), cada una restringida a los tipos de evento que tiene sentido que genere ese canal (por ejemplo, \texttt{POSProducer} -- tienda física -- solo genera \texttt{PURCHASE}).

\begin{sourcecode}[\label{code:producers}]{python}{Envío de eventos, ruteado por tipo (\texttt{productores/producers.py}).}
def send(self, event: Event) -> None:
    event["source"] = self.source
    topic: str = topic_for_event(event["event"])
    self.kafka.send(topic, key=event["user_id"], value=event)

class IoTProducer(BaseProducer):
    source = "iot"
    allowed_events = ["ADD_CART", "PURCHASE"]  # reposición automática

class POSProducer(BaseProducer):
    source = "pos"
    allowed_events = ["PURCHASE"]  # tienda física
\end{sourcecode}

\textbf{\texttt{main.py}: bucle principal.} Coordina todo lo anterior: crea los 5 productores y los 50 usuarios sintéticos, y en cada segundo recorre a cada usuario, decide si le toca generar un evento según su horario e intensidad (ajustada por la temporada activa), arma el evento y lo envía por el productor correspondiente.

\begin{sourcecode}[\label{code:mainloop}]{python}{Bucle principal del simulador (\texttt{main.py}).}
while True:
    now: datetime = datetime.now()
    season: Season = get_season(now.date(), forced=forced_season)
    for user in USERS:
        profile: AgentProfile = AGENTS[user["agent"]]
        if not args.ignore_horario and now.hour not in profile.hours:
            continue  # respeta horario del agente, salvo --ignore-horario
        if random.random() > 0.3 * profile.intensity * season.intensity:
            continue  # frecuencia según intensidad
        ev: Event = build_event(user, now, season)
        valid: list[BaseProducer] = [
            pr for pr in producers
            if pr.allowed_events is None or ev["event"] in pr.allowed_events
        ]
        pr: BaseProducer = random.choice(valid)
        pr.send(ev)
    time.sleep(1)
\end{sourcecode}

\section{Diseño de topics de Kafka (Fase 3)}
\label{sec:kafka-topics}

El diagrama de referencia del enunciado ("PROPUESTA: ARQUITECTURA ORIENTADA A EVENTOS") propone 4 topics dentro de Kafka: \texttt{user-events}, \texttt{purchase-events}, \texttt{iot-events} y \texttt{system-events}. En este proyecto se implementaron solo los dos primeros (ya usados en la Fase 2, Sección \ref{sec:fase2}), decisión que se justifica a continuación.

\texttt{user-events} y \texttt{purchase-events} separan el tráfico por semántica de negocio, no por canal de origen: el primero concentra la navegación (\texttt{SEARCH}, \texttt{VIEW\_PRODUCT}), el segundo la conversión (\texttt{ADD\_CART}, \texttt{PURCHASE}, \texttt{PAYMENT\_REJECTED}). Esto le da a Apache Flink (Fase 4) una separación natural entre análisis de navegación y análisis de conversión sin tener que filtrar un único topic mezclado.

\texttt{iot-events} no se implementó porque, en el diseño actual del simulador, los canales "IoT" y "Vehicle" (Sección \ref{sec:infraestructura}, \texttt{agentes-simulador/src/productores/producers.py}) representan medios de \textit{compra} (un agente comprando desde un dispositivo IoT o desde el auto), no telemetría real de sensores -- los eventos que publican son los mismos \texttt{SEARCH}/\texttt{ADD\_CART}/\texttt{PURCHASE} que cualquier otro canal. Crear un topic \texttt{iot-events} sin tráfico genuino habría sido solo para completar visualmente el diagrama de referencia, sin aportar contenido real que analizar.

\texttt{system-events} tampoco se implementó: las alertas que genera Apache Flink (Sección \ref{sec:flink}) no se publican de vuelta a Kafka, sino que se escriben directo a una tabla de PostgreSQL/TimescaleDB (\texttt{alertas}), que es lo que Grafana consulta para el panel de alertas del dashboard (Sección \ref{sec:dashboard}). Un topic \texttt{system-events} habría sido un salto intermedio innecesario entre Flink y su propio destino final.

En síntesis: se prefirió una arquitectura con topics que reflejan tráfico real y verificable sobre una réplica exacta del diagrama de referencia con topics vacíos.

\section{Apache Flink: cluster y job de audiencias digitales (Fase 4)}
\label{sec:flink}

El cluster de Flink (1 JobManager + 3 TaskManagers) ya se desplegó y verificó en la Fase 1 (Sección \ref{sec:infraestructura}). Esta sección documenta el job que corre sobre ese cluster: consume los 2 topics de Kafka (Sección \ref{sec:kafka-topics}), procesa los eventos, y escribe los resultados a PostgreSQL/TimescaleDB para alimentar el dashboard (Sección \ref{sec:dashboard}).

\subsection{Diseño del job}

Todo el procesamiento vive en un único job de Flink, \texttt{AudienciasDigitalesJob} (paquete \texttt{com.bigdata.audiencias}, código completo en \href{https://github.com/Noodle96/Big_Data/tree/main/digital-audience-streaming-platform/flink-jobs}{\texttt{flink-jobs/} del repositorio}). Consume \texttt{user-events} y \texttt{purchase-events} como un solo stream unificado, filtra los eventos inválidos, y se ramifica en 4 líneas de procesamiento que comparten ese mismo stream de entrada:

\begin{enumerate}
\item \textbf{Agregación por ventana} (\texttt{windowAll}, ventanas tumbling de 10 segundos): cuenta eventos, usuarios distintos, vistas/compras por producto y compras por ciudad dentro de cada ventana.
\item \textbf{Clasificación de audiencias por usuario} (\texttt{keyBy(user\_id)} + estado acumulado de Flink): evalúa, en cada evento, en cuál de 6 categorías de negocio cae el usuario según su comportamiento acumulado.
\item \textbf{Alertas}: una anomalía de ventana (muchos \texttt{ADD\_CART} sin ningún \texttt{PURCHASE}) y una alerta cuando un usuario cambia a un estado de audiencia de riesgo o de alto interés.
\item \textbf{Join vista/compra}: cruza eventos \texttt{VIEW\_PRODUCT} y \texttt{PURCHASE} del mismo producto dentro de la misma ventana, como dato exploratorio adicional.
\end{enumerate}

\subsection{Estructura del código y componentes internos}

El diseño del job fue trabajo del integrante del equipo a cargo de la Fase 4; esta subsección recorre archivo por archivo, en el mismo orden en que se diseñó, el código real que corre hoy contra el cluster -- durante la integración se renombró el paquete (de \texttt{pe.unsa} a \texttt{com.bigdata.audiencias}, para que coincida con el resto del proyecto) y se cambió el destino final de cada rama, de tópicos de Kafka a tablas de PostgreSQL (ya explicado en la subsección anterior), pero la lógica de procesamiento en sí no cambió.

\textbf{Modelo de datos (\texttt{model/Event.java}, \texttt{model/WindowSummary.java}).} \texttt{Event} representa un evento individual tal como lo publica el simulador; la anotación \texttt{@JsonIgnoreProperties(ignoreUnknown = true)} le dice a Jackson que ignore cualquier campo del JSON que no reconozca en vez de fallar, y cada campo necesita su getter/setter porque Jackson los usa para llenar el objeto automáticamente. \texttt{WindowSummary} es el resultado agregado de una ventana completa: cuántos eventos hubo, cuántos usuarios distintos, y varios conteos agrupados (por tipo de evento, por ciudad, por producto).

\begin{sourcecode}[\label{code:event}]{java}{Campos del modelo \texttt{Event} (\texttt{model/Event.java}).}
@JsonIgnoreProperties(ignoreUnknown = true)
public class Event implements Serializable {
    private String timestamp;
    private String user_id;
    private String event;
    private String product;
    private String category;
    private String city;
    private double price;
    private String agent_type;
    private String source;
    // ... constructor vacio, getters y setters
}
\end{sourcecode}

\textbf{Deserialización (\texttt{model/EventDeserializer.java}).} Convierte los bytes crudos que llegan de Kafka en un objeto \texttt{Event} usando Jackson. El \texttt{ObjectMapper} se crea recién en \texttt{open()} y no en el constructor, porque Jackson no es serializable y Flink puede mover esta clase entre TaskManagers -- si se creara en el constructor, fallaría al intentar serializar la clase completa para distribuirla al cluster.

\begin{sourcecode}[\label{code:deserializer}]{java}{Deserialización JSON $\to$ \texttt{Event} (\texttt{model/EventDeserializer.java}).}
public class EventDeserializer implements DeserializationSchema<Event> {
    private transient ObjectMapper objectMapper;

    @Override
    public void open(InitializationContext context) {
        this.objectMapper = new ObjectMapper();
    }

    @Override
    public Event deserialize(byte[] message) throws IOException {
        if (objectMapper == null) {
            objectMapper = new ObjectMapper();
        }
        return objectMapper.readValue(message, Event.class);
    }
}
\end{sourcecode}

\textbf{Agregación por ventana (\texttt{processing/WindowSummaryFunction.java}).} Recorre todos los eventos que cayeron dentro de una ventana de 10 segundos y arma los conteos: por cada evento, suma al total, agrega el usuario al set de usuarios distintos, incrementa el conteo de su tipo, y según sea \texttt{PURCHASE}, \texttt{VIEW\_PRODUCT} o \texttt{ADD\_CART}, también lo suma a los mapas de compras por ciudad/producto o vistas por producto.

\begin{sourcecode}[\label{code:windowsummary-fn}]{java}{Conteo dentro de una ventana (\texttt{processing/WindowSummaryFunction.java}).}
for (Event e : elements) {
    total++;
    users.add(e.getUser_id());
    eventCounts.merge(e.getEvent(), 1L, Long::sum);
    switch (e.getEvent()) {
        case "PURCHASE":
            purchasesByCity.merge(e.getCity(), 1L, Long::sum);
            purchasesByProduct.merge(e.getProduct(), 1L, Long::sum);
            break;
        case "VIEW_PRODUCT":
            viewsByProduct.merge(e.getProduct(), 1L, Long::sum);
            break;
        // ... ADD_CART
    }
}
\end{sourcecode}

\textbf{Clasificación de audiencias (\texttt{processing/ClassifyAudienceFunction.java}).} Mantiene, por usuario, un estado persistente de Flink (\texttt{ValueState}) con sus conteos acumulados de \texttt{SEARCH}/\texttt{VIEW\_PRODUCT}/\texttt{ADD\_CART}/\texttt{PURCHASE}, y en cada evento nuevo reevalúa en qué categoría cae. Cuando la categoría cambia hacia un estado de riesgo o de alto interés, emite una alerta por un side output aparte, para no mezclar el stream principal de audiencias con el de alertas. La única diferencia real frente al diseño original es la salida: antes se armaba un \texttt{Map} y se serializaba a JSON con Jackson para mandarlo a un tópico; ahora se devuelve un objeto \texttt{AudienceRecord}/\texttt{AlertRecord} tipado, porque el sink JDBC necesita enlazar cada campo directo a una columna SQL, no un blob de texto.

\begin{sourcecode}[\label{code:classify-fn}]{java}{Alerta al cambiar de audiencia (\texttt{processing/ClassifyAudienceFunction.java}).}
String previous = lastAudienceState.value();
if (!audiencia.equals(previous) &&
        (audiencia.equals("riesgo_abandono") || audiencia.equals("alta_intencion_compra"))) {
    ctx.output(alertTag, new AlertRecord(
            "audiencia",
            "Usuario " + value.getUser_id() + " cambio a audiencia: " + audiencia,
            value.getUser_id()));
}
lastAudienceState.update(audiencia);
\end{sourcecode}

\textbf{Join vista/compra (\texttt{processing/ViewPurchaseJoinFunction.java}).} Cruza, dentro de la misma ventana, un evento \texttt{VIEW\_PRODUCT} y uno \texttt{PURCHASE} del mismo producto -- correlaciona quién vio un producto con quién terminó comprándolo, aunque sean usuarios distintos. Mismo cambio que en la función anterior: el resultado ahora es un objeto tipado (\texttt{RelatedProductRecord}) en vez de JSON.

\begin{sourcecode}[\label{code:join-fn}]{java}{Correlación vista/compra (\texttt{processing/ViewPurchaseJoinFunction.java}).}
public RelatedProductRecord join(Event viewed, Event purchased) {
    return new RelatedProductRecord(
            viewed.getProduct(), viewed.getUser_id(), purchased.getUser_id());
}
\end{sourcecode}

\textbf{Orquestación (\texttt{jobs/AudienciasDigitalesJob.java}, la clase \texttt{Main} del diseño original).} Conecta todo lo anterior con la fuente de Kafka. Primero filtra eventos inválidos (usuario o tipo de evento vacío, precio negativo):

\begin{sourcecode}[\label{code:main-validacion}]{java}{Limpieza y validación (\texttt{jobs/AudienciasDigitalesJob.java}).}
DataStream<Event> events = raw.filter(e ->
        e != null &&
        e.getUser_id() != null && !e.getUser_id().isEmpty() &&
        e.getEvent() != null && !e.getEvent().isEmpty() &&
        e.getPrice() >= 0
).name("validacion-eventos");
\end{sourcecode}

Luego arma la ventana de agregación:

\begin{sourcecode}[\label{code:main-ventanas}]{java}{Ventanas y agregación (\texttt{jobs/AudienciasDigitalesJob.java}).}
DataStream<WindowSummary> summaries = events
        .windowAll(TumblingProcessingTimeWindows.of(WINDOW_SIZE))
        .process(new WindowSummaryFunction())
        .name("agregaciones-ventana");
\end{sourcecode}

La rama del join, filtrando primero cada tipo de evento por separado:

\begin{sourcecode}[\label{code:main-join}]{java}{Vistas y compras cruzadas (\texttt{jobs/AudienciasDigitalesJob.java}).}
DataStream<Event> viewed = events.filter(e -> "VIEW_PRODUCT".equals(e.getEvent()));
DataStream<Event> purchased = events.filter(e -> "PURCHASE".equals(e.getEvent()));

viewed.join(purchased)
        .where(Event::getProduct).equalTo(Event::getProduct)
        .window(TumblingProcessingTimeWindows.of(WINDOW_SIZE))
        .apply(new ViewPurchaseJoinFunction())
        .sinkTo(makeRelatedSink(jdbcUrl, jdbcUser, jdbcPassword));
\end{sourcecode}

Y la rama de audiencias por usuario, con su side output de alertas:

\begin{sourcecode}[\label{code:main-audiencias}]{java}{Audiencias por usuario (\texttt{jobs/AudienciasDigitalesJob.java}).}
OutputTag<AlertRecord> alertTag = new OutputTag<AlertRecord>("alertas-audiencia") {};

SingleOutputStreamOperator<AudienceRecord> audienceStream = events
        .keyBy(Event::getUser_id)
        .process(new ClassifyAudienceFunction(alertTag))
        .name("clasificacion-audiencias");

audienceStream.sinkTo(makeAudienceSink(jdbcUrl, jdbcUser, jdbcPassword));
DataStream<AlertRecord> alertasAudiencia = audienceStream.getSideOutput(alertTag);
\end{sourcecode}

\subsection{Por qué PostgreSQL/TimescaleDB y Grafana}

Esta decisión ya se adelantó en la Sección \ref{sec:arquitectura}, y aquí se retoma con más detalle porque es la que conecta directamente a Flink con el dashboard. Se evaluaron tres formas de alimentar la visualización: una arquitectura 100\% push vía WebSockets (el dashboard como un consumidor más de Kafka), un dashboard propio con Streamlit, o Grafana consultando una base de datos. Se eligió la tercera por dos razones concretas: Flink ya necesitaba escribir sus resultados a algún destino persistente (no solo transmitirlos), y PostgreSQL/TimescaleDB tiene un conector JDBC directo y maduro para Flink (\texttt{flink-connector-jdbc-postgres}, ya usado en la Fase 4) -- no hace falta ningún componente intermedio. TimescaleDB, al ser una extensión sobre PostgreSQL y no una base de datos aparte, agrega justo lo necesario para series de tiempo (particionamiento automático por tiempo vía \textit{hypertables}) sin obligar a aprender un lenguaje de consulta nuevo como InfluxQL/Flux. Grafana, por su parte, trae paneles, tipos de gráfico y alertas por umbral ya integrados -- se obtiene un dashboard con apariencia profesional sin escribir código de visualización propio.

\subsection{Cómo Grafana genera los paneles}

El dashboard completo está \textbf{provisionado como código}: no se creó ningún panel a mano haciendo clic en la interfaz de Grafana, todo vive en archivos versionados dentro de \href{https://github.com/Noodle96/Big_Data/tree/main/digital-audience-streaming-platform/dashboard/grafana}{\texttt{dashboard/grafana/}} del repositorio. Grafana funciona con dos piezas de configuración separadas:

\textbf{El datasource} (\texttt{dashboard/grafana/provisioning/datasources/postgres.yaml}) le dice a Grafana dónde y cómo conectarse a PostgreSQL: host, base de datos, usuario/contraseña, y que la base tiene TimescaleDB habilitado.

\textbf{El dashboard} (\texttt{dashboard/grafana/dashboards/audiencias-eventos.json}) define cada uno de los 10 paneles: su tipo (pie, barras, gauge, tabla, serie de tiempo, stat), su posición en la grilla, y -- lo más importante -- una consulta SQL propia por panel. Cuando el navegador carga el dashboard (o cada 30 segundos, por el auto-refresh configurado), Grafana ejecuta la consulta de cada panel contra PostgreSQL y dibuja el resultado según el tipo de panel. No hay caché ni copia de los datos dentro de Grafana: cada vez que se ve un panel, se está viendo el estado real de la tabla en ese instante.

Al arrancar Grafana, un tercer archivo (\texttt{dashboard/grafana/provisioning/dashboards/dashboards.yaml}) le indica dónde buscar los \texttt{.json} de dashboards -- así, con solo copiar los 3 archivos a las rutas reales de Grafana y reiniciar el servicio, el dashboard completo aparece solo, sin ninguna configuración manual:

\begin{enumerate}

\begin{lstlisting}[style=cmdbox]
cd ~/digital-audience-streaming-platform/agentes-simulador/src

Sin \texttt{--escenario}, el simulador detecta la temporada por la fecha real del sistema; en el momento de esta corrida cayó fuera de cualquier ventana comercial especial (\texttt{agentes-simulador/src/escenarios/seasons.py}), así que corrió en el escenario \textbf{"Normal"} -- el mismo punto de comparación base que pide la Fase 7 (Tabla \ref{tab:fases-plan}) para contrastar contra escenarios con boost de compras (Navidad, Cyber Monday, etc.).

\item \textbf{Corrida sostenida y cierre.} Se dejó correr el simulador durante ~15.5 minutos (\texttt{Ctrl+C} para detenerlo), tiempo suficiente para que las tendencias en Grafana muestren un patrón real en vez de 2-3 puntos sueltos.

El hallazgo más relevante de esta corrida no es un número aislado, sino un patrón: la clasificación de audiencias (Tabla \ref{tab:resumen-corrida}, última fila con datos) es \textbf{sensible al tiempo de observación}. Esto no invalida el resultado: confirma que el pipeline reacciona correctamente al comportamiento real de los usuarios, y es justamente el tipo de comparación que la Fase 7 (ejecución de varios escenarios) va a poder explotar -- contrastando esta corrida "Normal" contra corridas más cortas o con escenarios de temporada alta, donde se espera ver mayor variedad de audiencias y alertas de \texttt{riesgo\_abandono} más sostenidas en el tiempo.
