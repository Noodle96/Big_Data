\section{Infraestructura (Pulumi / AWS Academy)}

Toda la infraestructura del proyecto (Kafka, Flink, PostgreSQL/TimescaleDB y Grafana) se define como código con Pulumi (Python) y se despliega sobre AWS Academy. El script completo vive en \texttt{infra/\_\_main\_\_.py}; esta sección documenta el despliegue paso a paso, con la evidencia real de cada comando ejecutado.

\subsection{Despliegue con Pulumi}

Con el stack ya configurado, el despliegue completo se ejecuta con un solo comando:

\inlinesourcecodeboxed[cmdbg]{bash}{pulumi up --yes}

La Figura \ref{img:pulumi-up-1} muestra la creación de las 8 instancias EC2.

\insertimage[\label{img:pulumi-up-1}]{evidencia/pulumi-up-1.png}{width=14cm}{Resultado de \texttt{pulumi up --yes}: 8 recursos \texttt{aws:ec2:Instance} creados.}

La Figura \ref{img:pulumi-up-2} muestra los outputs exportados por el stack: bootstrap servers de Kafka, URLs de Flink y Grafana, e IPs de cada instancia.

\insertimage[\label{img:pulumi-up-2}]{evidencia/pulumi-up-2.png}{width=14cm}{Outputs de \texttt{pulumi up --yes}: endpoints y comandos SSH de cada instancia.}

Es importante notar que \texttt{pulumi up} terminando no significa que Kafka/Flink/Postgres/Grafana ya estén instalados y corriendo -- eso lo hace el script de \texttt{user\_data} (cloud-init) en segundo plano dentro de cada instancia, y toma varios minutos adicionales. Las siguientes subsecciones verifican, servicio por servicio, que ese proceso terminó correctamente.

\subsection{Verificación: Apache Kafka (KRaft)}

Los 3 brokers corren Kafka 3.9.0 en modo KRaft (sin Zookeeper), reutilizando el patrón validado en el laboratorio anterior del curso (incluyendo el fix del bug KAFKA-18281). Se verifica que el servicio systemd \texttt{kafka} esté activo en cada broker con \texttt{systemctl status}, forzando un pseudo-terminal (\texttt{-t}) para que la salida se trunque al ancho de la consola en vez de imprimir la línea completa del proceso Java:

\subsection{Verificación: PostgreSQL + TimescaleDB}

La instancia \texttt{dashboard} corre PostgreSQL 16 con la extensión TimescaleDB, que será el destino de los datos agregados que escriba Flink (Fase 4 del plan de trabajo). IP pública de esta instancia: 98.81.129.129.

\inlinesourcecodeboxed[cmdbg]{bash}{ssh -t -i ../keys/audiencias-lab-key.pem ubuntu@98.81.129.129 "sudo systemctl status postgresql --no-pager"}

\insertimage[\label{img:status-pg}]{evidencia/status-postgresql.png}{width=14cm}{Servicio \texttt{postgresql} (envoltorio de Debian/Ubuntu) activo.}

Ese servicio es solo un orquestador -- por diseño de los paquetes de Debian/Ubuntu queda en estado \texttt{active (exited)} en vez de \texttt{running}. Para confirmar que la instancia real de Postgres (\texttt{16/main}) está en línea:

\begin{lstlisting}[style=cmdbox]
ssh -i ../keys/audiencias-lab-key.pem ubuntu@98.81.129.129 "sudo pg_lsclusters"
\end{lstlisting}

\insertimage[\label{img:pg-lsclusters}]{evidencia/postgres-lsclusters.png}{width=14cm}{Cluster \texttt{16/main} en estado \texttt{online}, puerto 5432.}

Y que la extensión TimescaleDB quedó correctamente instalada en la base \texttt{audiencias}:

\begin{lstlisting}[style=cmdbox]
ssh -i ../keys/audiencias-lab-key.pem ubuntu@98.81.129.129 "PGPASSWORD='AudienciasLab2026!' psql -h localhost -U flink -d audiencias -c '\dx'"
\end{lstlisting}

\insertimage[\label{img:pg-timescale}]{evidencia/postgres-timescaledb-extension.png}{width=14cm}{Extensión \texttt{timescaledb} (v2.29.0) instalada en la base \texttt{audiencias}.}
